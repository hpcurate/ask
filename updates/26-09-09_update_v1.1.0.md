## What was done

A roving cursor over the controls of the screen you are on, on exactly the
bindings the comment names, with the arrow keys working alongside them.

**Left and right step between the three screens** — write, queue, sent — and
stop at the ends rather than wrapping, because wrapping from `sent` back to
`write` reads as a glitch rather than a move.

**Up and down walk the controls**, and the selected one wears the focus ring.
The scope is whatever owns the keyboard: an open sheet if there is one, else
the screen. A sheet is modal, so the cursor must not be able to walk out from
under it.

**Space uses the selected control** — a chip, a button, or stepping into a
field.

**Enter confirms a field and moves to the next**, and files the request when
there is no next one. That deliberately takes Enter away from the title, which
is a `<textarea>`: a newline in a request title is not something anyone wants,
and shift+Enter is still there for one.

### Two decisions worth keeping

- **The focusable list is rebuilt on every move, never cached.** These screens
  re-render on every change — a chip picked, a request queued, a card removed —
  and a cached list hands back nodes that have left the document. A miss
  restarts at the top, so the cursor heals rather than breaks.
- **A text field is selected but not focused.** The bindings are letters; a
  focused field would both swallow them and type them. The cursor stops on the
  field wearing the ring, space steps in, and Enter or Escape steps back out.
  That is also why the ring is a class rather than `:focus-visible` — on an
  unfocused field there is nothing for `:focus-visible` to paint.

### Rebindable

All five are settings, for the same reason ROOT's are: the defaults are a guess
about a layout, and a key under the finger on one keyboard is nowhere near it
on another. Settings captures the next key pressed rather than asking anyone to
spell `arrowup` into a text field, and a key already bound elsewhere is taken
off that action — two actions on one key means the first wins and the second
silently does nothing, which reads as a broken setting rather than a choice.

The arrows, Enter, Escape and Tab are **not** rebindable: they read the same on
every keyboard, so there is nothing to choose.

## Verification

`node test/smoke.mjs` — **49 checks passing**, 11 added.

Covered: the shipped bindings, the screen steps and their ends, the arrows
alongside the letters, Enter filing the form, a rebind taking effect and
freeing the key it replaced, the guard that keeps a bound letter typed into a
field from navigating, and the rebind rows being drawn from the same list the
keys come from.

**Not verified.** jsdom never populates `offsetParent`, so `focusables()` is
empty there and the cursor's **movement** cannot be driven at all — the same
limit ROOT's harness has. The ring itself, the walk between fields, and Enter
stepping to the *next* field rather than to the end of the form all need a
browser, and the extension would not connect. The logic underneath them is
covered; the walk is not.
