## What was done

### "One thing at a time" applies to a key too

1.4.0 put a link and an edit in the same box: both were "a whole request at
once", so both switched quick mode off. That was right about an edit and wrong
about a link. An edit really is a whole request handed over. A link is
**answers** — a key knows its project and its kind, and it does not know what
you want to say.

So a link keeps the flow now, and the flow asks only what is left:

- It **opens on the first question the link did not answer** — usually the
  request line itself.
- Answering a question **walks past** anything else the link already answered
  rather than asking it back, which is what would have made the setting mean
  nothing.
- Backspace still steps into every one of them, so nothing is out of reach.
- `notes` is never skipped: it is the last step and filing is what it does, so
  skipping it would file the request without ever showing it to you.
- `prio` counts as answered only when it is not p4, because p4 is also what an
  unanswered priority looks like.

Filing from the flow now ends the link the way filing from the long form
already did, so the next request in a run is a blank one.

One thing this needed that was not obvious: arming the flow from a link has to
**redraw** it. `paintQuick` only draws when the view was not already open, and
after a link it always is — so the question changed underneath and the screen
did not.

### The app fits a small window

ASK was laid out for one width. Under 560 it fills the window, which is the
right idea, but everything inside was a fixed pixel — an 18px gutter, a 34px
wordmark, a pill assuming 110px of margin either side — so a window dragged
narrow ran the wordmark into the count, squeezed the gutters and pushed the pill
past its own edge.

Everything is now expressed against the viewport instead of against one guess:

- **one gutter token**, `--gut`, read by the band, the scroller and the sheets,
  so they cannot drift apart at a width nobody tested;
- the **wordmark and its count** shrink together, and the count stops reserving
  a fixed width — they share a row and are the two things that collide first;
- the **pill**'s margin is itself a clamp, so at 320px there is still a bar;
- section heads, notes, labels, chips, buttons, cards and filter chips all
  scale;
- a **sheet** is measured against the window as well as the frame, because under
  560 the frame is not the window;
- nothing may push the page sideways — a request title is arbitrary text and is
  the likeliest thing to try, so it wraps anywhere;
- a **short** window gives the band up first, since every pixel it holds is one
  the quick view's answers cannot have.

`clamp` rather than a media query throughout: there is no width at which this
becomes a different app — it is the same app, smaller. The **upper bound of
every clamp is the number that was already there**, so at a comfortable width
nothing has moved.

### What was not done, and why

The comment asks to "make sure i can not resize the window". A Chromium `--app`
window cannot be made non-resizable — there is no flag for it and nothing on the
page can refuse a drag of the OS window frame. What the two tasks between them
actually needed was for the window to **arrive** small and centred, which the
plugin now does, and for the app to hold up when you drag it smaller, which is
this. Resizing is no longer something you have to do, and no longer something
that breaks anything — but it is still something you *can* do.

The added checks drive it: a link no longer switching quick mode off, the flow
